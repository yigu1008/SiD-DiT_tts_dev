## POST-MORTEM 2026-10-29: two of the three Jev roles were never tested (duplicate-panel bug)
Pulling one `logs/jev_calls.jsonl` record showed all three panels with the same reward (1.233) and the same VLM assessment.
Cause: both `jev_act.py` and `BankDecider.adjust_candidates` built the "one panel per distinct wording" sheet with
`for w in {wordings in trace.actions}: by_w[w] = best trace` -- a trace is registered under EVERY wording it used across its
8 segments, so the single best trajectory fills every slot. Measured on the logs / re-derived from records:
* `ja_jevact_v2w`: 648 decisions -- **62% of sheets were ONE image shown 3x, 27% two distinct, only 11% three distinct**
  (90% of calls had >=2 identical rewards, 99% identical assessments). Jev's order-permuted answers disagree accordingly
  (mean max spread 0.49): it was choosing among copies.
* `ad_jevbank`: 98 calls, **96% all-identical panels**.
* `ad_jevprobe`: panels are per-node probes, distinct by construction -- the only valid Jev test, but only 18 calls in total
  (2 per prompt; `wants_prior` fires during tree selection only, and the tree has few key-step nodes before rollout).
Consequences: the jevact (-0.45) and jevbank (-0.19) contrasts say nothing about Jev; they measure a random pick among
identical exemplars (which also explains why Jev collapsed exploration: the "winner" was always the same trajectory's
setting). The probe result (jevprobe -0.28 vs randprobe, 1/9) stands but is n=18 decisions. The "Jev adds nothing inside the
search" bottom line is therefore NOT established by these runs; the earlier A6000 `ja_jevact`/`ja_jevact_v2` arms used the
same code and are affected too.
Fix (committed): one panel per distinct TRACE, best-first, labelled by its dominant wording (mean CFG over that wording);
simulated on the recorded trajectories -> sheets are 60% two / 40% three distinct images, never one. Rerun needed:
`ja_jevact_v2w` (+ its random control, same code path) and `ad_jevbank`/`ad_randbank`; ~1.5 h + ~6 h on the 3-GPU node.
Lesson for RESUME.md: before any decider arm, assert in the sheet builder that panel images are pairwise distinct and log
the number of distinct images per decision.

## 2026-10-29 23:45 — Jev-side iteration plan (research pass; applies if the fixed rerun is still flat)
**What the Jev models are actually built for** (model card, `jev_omni.py`, DecisionBench card, OneJev `examples/request.json`, CondadosAI/jev-omni-eval):
* Typed decisions: `noul` (yes/no, one calibrated prob), `choice` (short keys, each with a criterion text), `score` (ordered levels
  0..5 with level descriptions). Several questions share ONE state. DecisionBench states are long mixed-format text (1-19k chars);
  option keys are short snake_case labels explained in `criteria`. Jev-Omni renders `OPTIONS:\n1. <text>` and scores one head
  slot per option -> the option text IS what is discriminated (hence the 5117d46 change).
* Images: Jev-Omni's loader takes ONE image; jev-omni-eval passes several images as separate media entries (BLINK, up to 4) -- no
  stitching, state = "N images are attached, in order". The decision head is calibrated on text (ECE 0.03-0.04) but on image
  benchmarks it only matches the base model (BLINK -0.5, MMStar +0.6 pts) with ECE 0.09-0.14: image judgement is NOT where the
  head adds value; calibrated per-option probabilities are.
* OneJev-27B (OmniJev, the user's JevArena work): native multi-question-per-state API (`qev`), `<image:N>` markers in a dict state,
  Q8 GGUF (~29 GB + mmproj) served by llama-server reproduces the BF16 scores (0.641 vs 0.642 mean). On JevArena image leaves
  OneJev-27B beats Qwen2.5-Omni-7B on judge-type questions: agent_success (noul) 0.84 vs 0.74, preference (pairwise) 0.71 vs 0.40,
  grounding (choice) 0.77 vs 0.58; Qwen3.8-27B is competitive/better on preference (0.86). Jev-Omni-12B was not in that comparison.

**Where our usage departs from the training distribution**: one 3-way `choice` over a stitched contact sheet whose captions are
baked into the pixels; a long narrative state; the question asks for a comparative pick, not a typed judgement of one image.

**Iteration ladder (cheapest first; each step is an offline validation before any sampling):**
1. *Typed grading instead of comparative choice.* Per candidate image: `score` "how well does this image satisfy the prompt"
   (0..5, levels written from the prompt's elements) + one `noul` per prompt element from a checklist ("the image shows four
   dresses"). Decision = argmax of calibrated score / fraction of satisfied elements. This uses the head where it is good
   (calibrated typed answers) and gives REASONS (which element failed) for a proposer. Validate offline on the 72 judged images
   (8 arms x 9 prompts): correlation of Jev score / element pass-rate with VQAScore and Qwen alignment, vs HPSv3's 0.0-0.1.
2. *Images as separate media, not a sheet.* Pass panels as individual images (jev-omni-eval path) with a short structured state;
   keep captions out of the pixels. Check on the same 72 images that the single-image score is stable (order permutation spread).
3. *Model swap test.* Run step 1's questions through OneJev-27B Q8 GGUF (llama-server on GPU1 replaces Jev-Omni's 23 GB) and
   compare the same offline correlations; also Qwen2.5-VL-7B asked the same typed questions via its logits (the VLM is already up).
4. Only then put the winner into the sampler -- as the grader in the layer-2 fidelity channel (z0 fixed), never as the action
   policy. NFE-matched bo-k remains the control.
Sources: HF akhilaaa3/Jev-Omni card; huggingface.co/datasets/akhilaaa3/decision-bench; github.com/CondadosAI/jev-omni-eval
(src/eval_img.py); $WORK/jevarena_img_smoke/JevArena_model_comparison_root500.md; OneJev model_card.md + examples/request.json.
